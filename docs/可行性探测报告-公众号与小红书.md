# 一、公众号文章 —— ✅ 完全可行，而且比知乎简单

## 1.1 实测数据

用一条真实文章链接测试（`https://mp.weixin.qq.com/s/ufyjJQJtqCh9RMo489O6bg`）：

```
HTTP 200
响应大小    4,558,365 字节（4.3 MB）
正文区      504,295 字节
段落数      92 个 <p>
图片数      40 张
标题区      id="activity-name"     ✓ 存在
正文区      id="js_content"        ✓ 存在
```

**一次普通 curl 请求就拿到了完整 HTML，没有跳转、没有验证码、没有 403。**

## 1.2 图片防盗链测试

```
无 Referer 下载 → HTTP 200, 128,899 字节, JPEG 1080x1080  ✓
带 Referer 下载 → HTTP 200, 128,899 字节, JPEG 1080x1080  ✓
```

**结论：图片完全没有防盗链，连 Referer 都不用带。这比知乎宽松得多。**

## 1.3 两种链接格式都能用

| 格式 | 示例 | 状态 |
|---|---|---|
| 短链 | `mp.weixin.qq.com/s/ufyjJQJtqCh9RMo489O6bg` | ✓ 可直接抓 |
| 长链 | `mp.weixin.qq.com/s?__biz=Mzxx&mid=xx&idx=1&sn=xx` | ✓ 同样可抓 |

## 1.4 技术路线（最简）

```
输入 URL
  ↓
curl/fetch 直取 HTML（带 Chrome UA）
  ↓
解析 #activity-name → 标题
解析 #js_content  → 正文 DOM
  ↓
DOM → Markdown（复用 zhihu-md.mjs 的 block() 转换器）
  ↓
图片：data-src 属性 → 下载 → 本地化（复用 localizeImages）
```

**完全不需要浏览器！比知乎还简单一个层级。**

## 1.5 需要处理的坑

| 坑 | 说明 | 解法 |
|---|---|---|
| **图片是 `data-src`** | 不在 `src` 里，是懒加载 | 优先读 `data-src`，回退 `src` |
| **样式全内联** | 公众号用 `style="..."` 控制排版，转 MD 要丢掉 | 只取文本结构，忽略 style |
| **有 `<section>` 嵌套** | 排版用 section 层层包裹 | 递归遍历，section 当 div 处理 |
| **代码块是 `<pre><code>`** | 跟知乎一样 | 复用现有逻辑 |
| **部分图片是 GIF** | 表情包常见 | 按魔数嗅探扩展名（已有 sniffImageExt） |
| **文章可能被删** | 返回"该内容已被发布者删除" | 检测关键词，明确报错 |
| **`vercel` 有临时参数** | `tempkey` 参数有时效 | 优先用永久链接 |

## 1.6 工作量估计

| 任务 | 时间 |
|---|---|
| 新建 `wechat-md.mjs`（主要是选择器） | 4 小时 |
| 复用 doc-export / localizeImages | 1 小时 |
| 接进 CLI + UI 标签页 | 3 小时 |
| 测试 10 篇文章（含长文、图文、代码文） | 2 小时 |
| **合计** | **1 天** |

## 1.7 结论

**做。这是投入产出比最高的一项。**

- 技术难度：**低**（比知乎低）
- 市场需求：**大**（自媒体、知识库、做资料的人天天要）
- 建议定价：**39.9**（和知乎同价，或打包成"长文合集"69.9）

# 二、小红书 —— ⚠️ 需要登录态，技术可行但成本高

## 2.1 实测数据

### 测试 1：直接 curl 首页

```
GET https://www.xiaohongshu.com/explore
→ HTTP 302
→ Location: /website-login/captcha?verifyType=124&...
```

**被重定向到验证码页。**

### 测试 2：浏览器打开首页

```
Page.navigate → https://www.xiaohongshu.com/login?redirectPath=...
页面标题    小红书 - 你的生活兴趣社区
__INITIAL_STATE__ 存在  ✓
含笔记数据  ✗
图片数量     0
正文        133 字（全是登录界面文字）
```

**跳到登录页，页面里没有任何笔记内容。**

### 测试 3：浏览器打开具体笔记页

```
https://www.xiaohongshu.com/explore/64857fe60000000027011081
→ 跳转到 /404/sec_xxx
→ error_code=300031
→ error_msg=「当前笔记暂时无法浏览」
```

**注意这个错误码：`300031`。这不是"文章被删"，而是"防爬拦截"。**
同一个 ID 通过搜索引擎能访问，说明内容还在，只是拒绝无登录态的直接访问。

## 2.2 结论

| 访问方式 | 结果 |
|---|---|
| 纯 HTTP（curl） | 302 → 验证码页 |
| 真浏览器 + 反检测 | 跳登录页，无数据 |
| 真浏览器 + 具体笔记 | 404 + error_code 300031 |
| **带登录 cookie** | **未测（本机无登录态）** |

**小红书对无登录态做了三重拦截，比知乎严格得多。**

## 2.3 唯一的可行路线

```
方案 A：持久化 profile + 用户手动登录一次
  1. 第一次运行 → 打开浏览器 → 用户扫码登录
  2. profile 存到本地（同知乎的做法）
  3. 后续用这个 profile 抓取
  4. 需要处理：cookie 过期、x-s 签名（登录后接口仍要签名）
```

**这是唯一现实的路，但有几个硬成本：**

| 成本项 | 说明 |
|---|---|
| **用户必须登录** | 每个买家都要扫码一次，转化率会掉 |
| **cookie 会过期** | 通常几天到几周，过期就要重新登 |
| **x-s 签名** | 登录后调 API 仍要算 `x-s`/`x-t`，需要从 JS 里抠算法 |
| **风控严格** | 批量抓会封号，买家账号有风险 |
| **DOM 提取更稳** | 走页面 DOM 而不是 API，能绕开签名，但滚动加载复杂 |

## 2.4 DOM 方案 vs API 方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **DOM 提取** | 不用逆向 x-s，登录后直接读页面 | 滚动加载、多图轮播、webp 格式 |
| **API 调用** | 结构化数据，字段全 | 必须算 x-s 签名，风控严 |

**建议 DOM 方案**，理由：签名算法会变，DOM 结构相对稳定。

## 2.5 需要解决的问题清单

```
□ 登录态持久化（profile 目录）
□ 登录引导（首次弹窗 + 用户扫码）
□ 笔记页等待加载（图片懒加载、瀑布流）
□ 图片：webp → 需要转 jpg 或保留原格式
□ 视频：笔记视频的地址在 DOM 的 <video> 里
□ 图文：多图轮播要全部取出
□ 登录失效检测（跳登录页就提示用户）
□ 批量抓取的间隔控制（防风控）
```

## 2.6 工作量估计

| 任务 | 时间 |
|---|---|
| 登录态持久化 + 引导 | 1 天 |
| 笔记页 DOM 提取 | 2 天 |
| 图片/视频下载 + 格式处理 | 1 天 |
| 登录失效检测 + 重试 | 0.5 天 |
| 风控控制 + 测试 | 1.5 天 |
| **合计** | **6 天** |

## 2.7 结论

**做，但排在公众号之后，并且要接受三个现实：**

1. **每个买家必须自己登录一次**（不能像知乎那样可选）
2. **cookie 会过期**，需要引导重新登录
3. **定价要高**（69.9~99），因为维护成本高
