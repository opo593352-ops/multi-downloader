## 三、架构

```
下载器UI.exe (C# WinForms, 5 个标签页 + 授权菜单)
    │  拼参数，起子进程
    ├─→ 下载器.exe video <url>   → engines/douyin-dl.mjs  （自带浏览器/CDP）
    ├─→ 下载器.exe music search  → engines/music-dl.mjs   （纯 HTTP）
    ├─→ 下载器.exe sites <url>   → engines/video-dl.mjs   （yt-dlp + ffmpeg）
    ├─→ 下载器.exe grab <url>    → engines/web-grab.mjs   （自带浏览器/CDP）
    ├─→ 下载器.exe zhihu <url>   → engines/zhihu-md.mjs   （+ doc-export）
    ├─→ 下载器.exe license ...   → dev/license.mjs        （卡密）
    └─→ 下载器.exe report "..."  → dev/report.mjs         （错误上报）
                                        ↑
                              全是同一个 SEA 单文件
                              （cli.mjs 静态 import 七个模块）
```

### 3.1 激活闸门在哪（v1.0.1 起是**两层**）

**第一层：`src/cli/cli.mjs` 的 `main()`**，分派之前。这一层只管体验（提示清楚），
不再是唯一防线。

```js
import { BUILD_INTERNAL } from '../dev/buildflag.mjs';

const selftestBypass = BUILD_INTERNAL && process.env.DSH_DL_SELFTEST === '1';
const activated = !!(licState && licState.activated) || selftestBypass || BUILD_INTERNAL;
if (!activated && !isLicenseCmd && !wantsHelp) { printLockedNotice(); process.exit(2); }
```

**第二层：每个引擎的 `run()` 开头自己验**（`src/dev/gate.mjs`）。

```js
export async function run() {
  assertFeature('music');   // ← 六个引擎各一行
  await main();
}
```

第二层验的不是布尔值，是**材料**：

```
ticket = HMAC-SHA256(SECRET, 'feat|v1|' + feature + '|' + blob.d)
```

`blob.d` 来自激活码（一卡一份），`SECRET` 来自 `dev/secret.mjs`（AES-GCM 封装）。
票还要落到真实路径上（临时目录名 / profile 目录名），拿不到票任务直接开不了工。

**实测验证**（2026-10-27）：

| 攻击方式 | 结果 |
|---|---|
| 把 cli 的 `if (!activated…)` 改成 `if (false)` | **仍被拦**，引擎报"music 不可用：尚未激活"，exit=2 |
| 再把 `checkFeature` 改成 `return {ok:true}` | **仍被拦**，`tempWorkDir` 拿不到票，抛 ELOCKED |

放行路径（三条）：

| 条件 | 用途 |
|---|---|
| `licState.activated` | 正常激活（含 blob 校验） |
| `BUILD_INTERNAL === true` | 内测版，**编译期常量**，见 `dev/buildflag.mjs` |
| `--help` / `-h` | 只打印帮助，不走下载路径；未激活用户必须能看到怎么激活 |

**为什么内测版用编译期常量**：`build.sh` 覆写 `dev/buildflag.mjs`，
esbuild `--minify` 把 `BUILD_INTERNAL ? … : null` 折叠成 `null`，
发布版里连分支字节都不剩。构建结束 `trap` 强制写回 false。

### 3.2 两个版本共用源码

```
src/cli/cli.mjs        → 下载器.exe        （BUILD_INTERNAL = false）
src/cli/cli-beta.mjs   → 下载器-beta.exe   （BUILD_INTERNAL = true）
```

`cli-beta.mjs` 由 `tools/make-internal-entry.mjs` 从 `cli.mjs` 生成，
只改两处：`BUILD_INTERNAL` 和 `VERSION` 后缀。

**好处**：不会出现「改了内测版忘了正式版」。改 `cli.mjs` 后重跑
`make-beta.sh` 就自动同步。

## 四、卡密系统（订阅制）

### 4.1 六个档位

| 档位 | 天数 | 用法 |
|---|---|---|
| `day` | 1 | 日卡（试用） |
| `week` | 7 | 周卡 |
| `month` | 30 | 月卡（默认） |
| `quarter` | 90 | 季卡 |
| `year` | 365 | 年卡 |
| `forever` | 32767 | 永久卡（距 EPOCH 上限） |

### 4.2 卡密结构

```
XXXXX-XXXXX-XXXXX-YYYY
└──10位──┘└绑定┘└签名┘

前 10 位 = 3位到期日 + 7位随机
  到期日 = 距 2024-01-01 的天数，base32 编码
  3 位 base32 = 32768 天 ≈ 89 年，够用
```

**到期日为什么编码进随机段**：不写在明面上，用户看不出哪几位是日期，
没法猜着改；而且它参与 HMAC 签名，改一位签名就崩。

### 4.3 三道校验

```
1. 签名   HMAC-SHA256(SECRET, payload) 前 4 位
2. 机器码 payload 里 5 位绑定 vs 本机码
3. 到期   now > 到期日 23:59:59 → 拒绝
```

### 4.4 时间回拨防护

用户把系统时间调回过去，已过期的卡会复活。对策：

```js
// 每次校验都记录见过的最大时间戳到 clock.dat
// 发现当前时间 < maxSeen - 2天 → 判定篡改，拒绝
if (clock && nowRaw < clock.maxSeen - 2*86400000) {
  return { ok: false, reason: 'clock-rollback' };
}
```

**已知局限**：删掉 `%APPDATA%\UnifiedDownloader\` 整个目录会同时删掉
`license.txt` 和 `clock.dat`，时间记录重置。但用户也得重新激活，
实际影响有限。真要更硬需要联网校时或注册表多处冗余，对小规模不划算。

### 4.5 机器码（踩过大坑，务必看坑 11.5.5）

```
机器码 = MD5(hostname + CPU型号 + PROCESSOR_IDENTIFIER) 前 5 位大写
```

**三条铁律**：

1. 只用**稳定项**，CPU 型号拿不到就跳过，**绝不回退 PowerShell**
2. 首次算出就**落盘** `%APPDATA%\UnifiedDownloader\machine.txt`
3. 之后永远读缓存

刻意**不**包含内存总量、磁盘序列号——用户加内存、换硬盘不该导致卡密失效。

### 4.6 卡密参与真实运算

激活码里带一段用卡密派生 key 加密的 **CDN 镜像表**：

```
激活码 = BASE64(JSON{ k: 卡密, d: 密文, i: iv, t: tag })
key    = HMAC(SECRET, 'res|v1|' + 完整卡密)
```

改 `verifyKey` 返回 true → 解不出镜像表 → B站 CDN 不通时下载必失败。
**不是靠代码检查拦你，是缺料。**

### 4.7 发卡

### 4.8 密钥与闸门的加固（v1.0.1）

这一节回答一个问题：**"拿到源码的人能不能自己造卡密？"**

#### 4.8.1 SECRET 不再是"一眼可算"

**旧实现**（`license.mjs` 34~57 行，已删）：

```js
const SEG_MASK = 0x5a;
const SEGS = [[0x6f,0x62,0x6e,0x1b], …];
function buildSecret() {
  for (const seg of SEGS) for (const b of seg) out += String.fromCharCode(b ^ SEG_MASK);
}
```

一组字节 + 一个 XOR 常量。看到这段代码的人写三行就能打印出 SECRET：

```js
SEGS.flat().map(b => String.fromCharCode(b ^ 0x5a)).join('')
```

拿到 SECRET 就能签发任意档位、任意机器码的卡密，**整条销售线当场报废**，
而且不可挽回（已发出的卡密无法统一作废）。这比"改 return true"严重一个量级。

**现在**（`src/dev/secret.mjs`）：

```
32 字节材料（salt16 + info16）
  → 逐字节掩码 ^ (0xB7 ^ (i*37+11))
  → 按 PERM[32] 置换位置
  → scrypt(N=16384, r=8, p=1) 派生 32 字节 key
  → AES-256-GCM 解密 → 得到 SECRET
  → sha1(SECRET)[:8] 必须等于 '3187f764'，否则抛错
```

**关键设计**：
- **失败抛错，不回退默认值**。回退默认值是这类代码最常见的自毁方式 ——
  攻击者只要把材料改坏，就能拿到一个"已知"的密钥。
- **密钥值没变**（仍是 `584A33…1762`），已售出的卡密与激活码继续有效。
- `license.mjs` 和 `keygen.mjs` 共用这一份，不再各抄一套 XOR 表
  （旧代码两处必须手工同步，既容易漏改，又让密钥表在二进制里多出现一次）。

**验证**：调 `__secret()` 输出 `584A337BFE0FB7F734E61A2BCCF81762`，
sha1 前 8 位 `3187f764`，与旧实现完全一致；本机已激活的年卡照常通过。

**诚实的边界**：本地校验的东西一定能被内存 dump 出来。这里的目标不是"不可破"，
而是把"strings 一下就有"变成"必须先读懂整套还原流程"。

#### 4.8.2 闸门是多点，不是单点

见 3.1 节。要点：**每个引擎自己验，验的是材料（ticket），不是布尔值。**
新增功能时必须在 `run()` 开头加一行 `assertFeature('xxx')`，
否则那个功能就是漏网之鱼。

#### 4.8.3 混淆从 XOR 换成 AES-GCM

**旧实现**：`__ds` 的密钥 `0x5c` 和算法全在明面上，写个循环就能批量解出
30 个敏感串（镜像域名、上报邮箱、接口路径）。

**现在**：AES-256-GCM，内容密钥构建期随机生成、打散成 8 个数字存放，
每段密文自带 iv + tag。改一个字节解不开。

**实测**（v1.0.1 产物，与裸 `node.exe` 基线对比）：

| 关键词 | 下载器.exe | 下载器-beta.exe | 卡密生成器.exe |
|---|---|---|---|
| `upos-sz-mirror` | 0 | 0 | 0 |
| `mountaintoys` | 0 | 0 | 0 |
| `CDP timeout` | 0 | 0 | 0 |
| `yt_dlp` | 0 | 0 | 0 |
| `bilivideo` | 0 | 0 | 0 |
| `a_bogus` | 0 | 0 | 0 |
| `aweme/v1/web` | 0 | 0 | 0 |
| `sjsjdj173` | 0 | 0 | 0 |
| `584A33…1762`（SECRET 明文） | 0 | 0 | 0 |
| `res\|v1\|` | 0 | 0 | 0 |
| `createDecipheriv` | 基线 3 | 基线 3 | 基线 3 |

`createDecipheriv` 的基线是 Node 运行时自带的（`node.exe` 里就有 3 个），
不是我们的泄漏。`internal-build` 只在 beta 里出现 1 次 —— 那是内测版自己的
状态串，正式版里是 0。

#### 4.8.4 还剩什么风险（必须承认）

| 风险 | 现状 | 能不能再抬 |
|---|---|---|
| 内存 dump 拿 SECRET | 无解（本地校验的通病） | 只能上联网校时 |
| 重实现整条派生链 | 门槛已从"10 秒"抬到"几小时" | 可加白盒密码学，成本高 |
| 直接 patch 掉 gate | 需同时改 6 处 + 伪造票 | 再加校验点收益递减 |
| 卡密转发 | 绑定机器码，换机失效 | 已够用 |

**真要更强只有一条路**：联网签发 runtime token。会引入服务器成本和离线不可用问题，
当前规模不划算 —— 这是取舍，不是遗漏。

## 六、踩过的坑（按痛苦程度排序）

> 这一节是本文档最有价值的部分。每条都是真踩过、真修过的，
> 不是"可能发生"的猜测。遇到怪现象先来这里搜关键词。

### 🔴 0. CDP 的 60 秒定时器没清 → 进度条"卡死"

`CDP.send()` 每次调用挂一个 60 秒超时定时器，但响应回来从不 `clearTimeout`、
也没 `unref`。任务干完进程还要空转一整分钟才退出，UI 卡在 `WaitForExit()`。

| 场景 | 修前 | 修后 |
|---|---|---|
| 引擎 `zhihu` | 66.65 s（抓取本身 6.6 s） | 7.12 s |
| UI 知乎端到端 | 68.5 s | 8.0 s |

```js
const timer = setTimeout(() => { ... }, 60000);
timer.unref();                              // 关键
this.pending.set(id, { resolve, reject, timer });
// 收到消息时
if (timer) clearTimeout(timer);
```

三处都要改：`zhihu-md.mjs`、`douyin-dl.mjs`、`waitForWs()` 的 3 秒超时。
另外加 `cdp.close()` 和 `flushAndExit()` 兜底。

### 🔴 1. 单 EXE 里动态 import 必挂

```js
await import(spec.module)   // ✗ 打包后仍去磁盘找文件
```

必须**静态 import + 查表**。

### 🔴 2. postject 前不移签名 → 进程被 Windows 阉割

现象 `EPERM mkdir` + `exit=0x80000003 STATUS_BREAKPOINT`。

```bash
signtool remove /s 目标.exe    # 必须在 postject 之前
```

**在 MSYS/Git-Bash 里要写 `//s`**，否则 bash 把 `/s` 转成路径，
signtool 只打印帮助、签名纹丝不动，postject 报 `signature seems corrupted`
——看着像成功实则踩坑。验证：`signtool verify /pa`，无索引项才算干净。

### 🔴 3. 「ffmpeg 已下载」可能只是源码包

`ffmpeg-9.0.2` 目录看着像 ffmpeg，实际是**源码**（只有 `configure` 和 `.c`）。
拿成品的省事途径：

```bash

87.6 MB，gyan.dev essentials build，**GPLv3**（分发需附源码声明）。

B站视频流常给随机域名（`xxx.edge.mountaintoys.cn:4483`），某些网络到这种
非标准端口直接超时。换官方镜像就通：

`video-dl.mjs` 里有镜像表，下载前 Range 探活，不通逐个试。
**只对已知站点生效**（乱换域名会变 SSRF）。

### 🔴 5. yt-dlp 探测的三个陷阱

**① `--version` 被留在参数里**

```js
// ✗ 运行时变成 yt_dlp -J ... --version，只打版本号
probe(py, ['-m','yt_dlp','--version'])
```

prefix 与探测参数必须分开。

**② 绝不能试 `py`**

Windows 的 `py.exe` 是 Python Manager，没装对应版本会**自动联网安装
Python 3.15**（实测触发过）。只用 `python` / `python3`。

**③ `python` 可能是假的**

常被 Microsoft Store 别名劫持。探测失败后扫
`%LOCALAPPDATA%\Python\pythoncore-*\python.exe`。

### 🔴 6. ProcessStartInfo.EnvironmentVariables 遇 NO_PROXY/no_proxy 抛异常

Windows 环境变量不区分大小写，系统里常同时有 `NO_PROXY` 和 `no_proxy`：

```

**不是自检专属问题**，任何有重复大小写变量的用户都会踩到。
修法：别碰 `EnvironmentVariables`，用进程级：

### 🟠 11. 想「不抢焦点」，子进程里怎么改都没用

覆写 `ShowWithoutActivation`、`ShowWindow(SW_SHOWNOACTIVATE)`、事后最小化
——全无效。激活发生在窗口创建时，由**父进程**的 `STARTUPINFO` 决定：

```csharp
si.dwFlags = STARTF_USESHOWWINDOW;   // 1
si.wShowWindow = SW_SHOWNOACTIVATE;  // 4
CreateProcess(exe, cmdLine, ..., ref si, out pi);
```

| 启动方式 | 焦点被抢采样数 |
|---|---|
| `Process.Start` 默认 | 39 / 39 |
| 子进程内 `--no-activate` | 39 / 39 |
| 父进程 `SW_SHOWNOACTIVATE` | **0 / 39** |

### 🔴 11.5. 通用抓取的「正文」选错了元素

观网文章抓出来只有 **9 字**，容器是 `<ul>` —— 抓到导航菜单了。

根因是旧版打分只看「文字多、标签少」：

```js
score = txt.length / Math.sqrt(childCount);   // ✗ 导航菜单分数极高
```

而选择器链更糟：`[class*="content"]` **先匹配到** `class="content"` 的导航，
真正的正文在 `class="content all-txt"`。

实测三个候选的对比（观网）：

| 容器 | 内容 | 性质 |
|---|---|---|
| `class="content"` | 9 字 | 导航菜单 `<ul>` |
| `class="content all-txt"` | 1859 字 | **真正文** |
| `class="article-other"` | 侧栏 | 责任编辑 + 相关推荐 |

修法（Readability 简化版）：

```js
let score = txt.length / Math.sqrt(childCount);
score *= (1 - linkDensity * 1.5);   // 链接多 → 扣分（导航全是链接）
score *= (0.6 + pDensity * 1.2);    // <p> 多 → 加分（正文是段落）
if (tag === 'ARTICLE') score *= 1.25;
```

外加：
- 候选池从 `div,section` 扩到所有块级（含 `td`）
- 类名/ID 含 `comment|sidebar|nav|menu|related|advert` 的直接跳过
- 优先 `article` / `[itemprop="articleBody"]` / `[role="main"]`

修完：**9 字 → 1859 字**。

**教训**：正文提取不能只看"字多"。必须看**链接密度**和**段落密度**。

### 🔴 11.5.5. 同一台机器算出两个机器码（灾难级）

`license status` 报 `25C2B`，`grab` 报 `C7998` —— **同一个 EXE，同一台机器**。

后果：客户激活后换个功能就提示「机器码不匹配」，等于软件不可用。

根因：

```js
MD5(hostname + cpuModel() + PROCESSOR_IDENTIFIER)
// cpuModel() 在 os.cpus() 返回空时回退 PowerShell
// PowerShell 返回的字符串和 os.cpus()[0].model 不完全一样
```

而 `grab` 启动 Chrome 占满 CPU 时，`os.cpus()` 可能短暂返回空 → 触发回退 →
CPU 型号字符串变了 → 整个机器码变了。

修法三条：

1. **算法只用稳定项**：`hostname + PROCESSOR_IDENTIFIER + arch`
2. **CPU 型号可选**：能拿到就加，拿不到就跳过，**绝不做 PowerShell 回退**
3. **首次算出就落盘**，之后永远读缓存

验证：删缓存重算 3 次，都是 `25C2B`。

**教训**：机器码这种东西，宁可少几个特征项，也不能有任何不确定性。
凡是"运行时可能失败然后走回退分支"的逻辑，都会让标识漂移。

断网/代理不通时，Chrome 渲染一个 `chrome-error://chromewebdata/` 页面，

if (href.startsWith('chrome-error://') || href.startsWith('chrome://')) {

### 🔴 19. 小说站对 Node 的 TLS 指纹降速 → 只能用 curl 子进程

**2026-10-27 实测，这个问题耗了整整两个小时。**

**现象**：`novel-dl.mjs` 下载 30 章，只成功 7 章，其余全部超时挂起。

**排查过程（三次对比）**：

| 方式 | 结果 |
|---|---|
| `curl` 连续 8 次 | **全部 200，每次 1.7 秒** ✅ |
| `Node fetch`（undici）连续 15 次 | 前 7 次正常 0.5~1.3 秒，**第 8 次后开始挂** |
| `Node https` 原生模块 | **第 1 次就超时 22 秒**，第 3/4/5 次全超时 |

**根因**：站点对 **Node.js 的 TLS ClientHello 指纹**做了识别和降速处理。
curl 用 OpenSSL + 完整浏览器头，Node 用自己的 TLS 栈，特征不同。

**试过但无效的方案**：

- `Connection: close` —— 无效
- `keepalive: false` —— 无效
- `agent: false` —— 无效
- 加大超时到 60 秒 —— 无效（连接被静默丢弃，不是慢）

**可行方案**：改用 `curl` 子进程。

```js
function curlGet(url, referer, timeoutMs) {
  return new Promise((resolve, reject) => {
    const args = [
      '-sS', '-L',
      '--max-time', String(Math.ceil(timeoutMs / 1000)),
      '--connect-timeout', '15',
      '-A', UA,
      '-H', 'Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8',
      '-H', 'Accept-Language: zh-CN,zh;q=0.9',
      '-H', 'Connection: close',
    ];
    if (referer) args.push('-H', 'Referer: ' + referer);
    args.push(url);

    const p = spawn('curl', args, { windowsHide: true });
    const out = [];
    p.stdout.on('data', (c) => out.push(c));
    p.on('close', (code) => {
      if (code !== 0) return reject(new Error(`curl exit ${code}`));
      const buf = Buffer.concat(out);
      if (buf.length < 200) return reject(new Error(`响应过短 (${buf.length}B)`));
      resolve(buf);
    });
  });
}
```

**依赖**：Windows 10 1803+ 自带 `curl.exe`，无需额外安装。
启动时用 `where curl` 探测一次（`haveCurl()`）。

**v1.0.1 修**：旧版探测了 `haveCurl()` 却**从来没用这个结果**（`CURL_OK` 是死变量），
没装 curl 的系统上直接满屏 `spawn curl ENOENT`。现在 `httpGet()` 会按
`CURL_OK` 分流，不可用时降级到内置 `fetch`（慢一些但能跑），并且只提示一次。

**当前状态**：单章 1~2 秒，10 章 24 秒正常。
但**整本 152 章连续下载仍会中途变慢**，推测是站点对同一 IP 的累计请求数限流，
需要在章节循环里加更长间隔（现在默认 `--delay 800`），或分段下载。

**同类风险**：以后遇到「curl 能通、Node 挂起」的站点，直接上 curl 子进程，别在 TLS 层浪费时间。

### 🟠 23. 探活定时器没清 → 进程多空转十几秒（v1.0.1 修）

### ✅ 25. 两张卡不累加，长卡会被短卡吃掉（**v1.1.0 已修：改成真累加**）

**实测**（2026-10-28，完整端到端）：

```
卡A 月卡（到期 11-27）激活 → 剩 31 天
卡B 月卡（到期 12-27）激活 → 剩 61 天    ← 不是 31+30=91，是覆盖
```

**根因**（`license.mjs` 的 `activate()`）：

```js
saveLicense(code, dec.blob);   // 直接覆盖，没有"读旧到期日再取较晚者"的逻辑
```

**更糟的场景**：

```
年卡激活 → 剩 366 天
再用日卡 → 剩 2 天      ← 白丢 364 天，用户一定来投诉
```

**为什么不能简单改成"相加"**：卡密里的到期日是**绝对日期**（编码在前 3 位 base32），
不是"时长"。真要累加得改卡密结构存天数，那**所有已发出的卡密都会失效**。

**建议方案（A+C，不破坏现有卡密）**：

- **A. 取较晚的到期日**：新卡到期 > 旧卡才覆盖，否则保留旧的
- **C. 覆盖前提示**：弹窗「当前剩 366 天，新卡只有 1 天，确定覆盖？」

~~改动约 10 行（`activate()` 加比较 + UI 加确认框）。**等拍板再动手**。~~

#### 实际改法（v1.1.0，用户拍板"改成累加"）

**核心难点**：卡密里原来只有**绝对到期日**，没有"这张卡值多少天"。
所以要做真累加，必须先让卡密带上时长。

**卡密格式改造**（payload 15 位）：

```
旧：到期日(3) + 随机(7)     + 机器码(5)
新：到期日(3) + 时长(2) + 哨兵'QZ'(2) + 随机(3) + 机器码(5)
              ↑0-1023天            ↑标记新格式
```

- **时长**：2 位 base32 = 0..1023 天（永久卡存 1023）
- **哨兵 `QZ`**：放在 payload[5..6]。旧卡这里是随机字符，撞上概率 1/1024；
  撞了也只是被当成"可累加卡"，最多多送几天，**不会让已购用户用不了**
  （误判方向是安全的）
- **3 位到期日不动** → 旧卡验签逻辑完全不受影响

**累加规则**（`activate()`）：

```
新到期 = max(今天, 旧到期) + 这张卡的时长
```

- 年卡剩 300 天 + 月卡 30 天 → 剩 330 天
- 已过期 + 月卡 30 天 → 剩 30 天
- **不是**"旧到期 + 时长"（那样过期三年的卡能白拿三年，等于补历史）

**累加后必须重签卡密**：不重签的话 `status()` 读的还是卡里原到期日，累加白做。

**⚠ 重签的坑（踩过一次）**：blob 是用 `deriveResourceKey(整张卡密)` 派生密钥加密的。
换了 code 就必须用**新 code** 重新加密 blob，否则存盘后
`unlockResource(新code, 旧blob)` 密钥不匹配 → `reason:'resource:decrypt'`
→ 表现为"激活成功、重启就失效"。已加 `resealBlob()` 解决。

**实测记录**（2026-10-29）：

| 场景 | 结果 |
|---|---|
| 年卡剩 364 天 + 月卡 30 天 | → **394 天** ✓ |
| 连续 3 张月卡 | 394→424→454→**484** ✓ |
| 日卡 1 天（验证不被吃掉） | 484 → **485** ✓ |
| 年卡 365 天 | 485 → **850** ✓ |
| 永久卡 | 31736 天，`stacked=false`（走绝对到期日，不该叠加）✓ |
| **老卡兼容**（本机年卡） | `additive=false durDays=0`，照常激活 ✓ |
| **老用户续费**（老卡+新季卡） | 364 + 90 = **454 天** ✓ |
| 打包版 EXE 端到端 | 364 → **393 天**，重启后仍 393 ✓ |

#### 累加带来的新漏洞：同一张卡可以无限刷（已修）

改成累加后暴露了一个严重问题：**同一张卡反复激活，每次都能加时长**。

实测（改之前）：

```
同一张月卡点 3 次：364 天 → 394 → 424 → 454    ← 白送两个月
```

以前是"覆盖"策略所以无害（重复激活结果不变），改累加后就成了刷时长漏洞。

**修法：记录已用卡密指纹**

- `%APPDATA%\UnifiedDownloader\used-cards.txt`，一行一个指纹
- 指纹 = `HMAC-SHA256(SECRET, 'used|v1|' + 卡密)` 前 16 位
  - 存哈希不存明文：万一这个文件流出去，也看不到卡密原文（卡密=钱）
  - 用 HMAC 不用裸 sha256：卡密空间有限，裸哈希能被离线穷举反查
- 判据：**指纹在列表里 + 本机已有有效激活 → 拒绝**

**为什么判据不是"比到期日"（踩过的坑）**：
累加规则是 `max(今天,旧到期)+时长`，所以同一张卡第二次激活算出的到期日
**永远比原来大**。一开始写的是 `alreadyUsed && 新到期 <= 旧到期`，
那个条件永不成立，防重放形同虚设 —— 实测连点 3 次照样涨到 454。

**必须留的恢复路径**：用户重装系统/删配置后，要用原卡恢复授权。
所以判据加了 `&& prevExpiry`（本机已有激活才拒绝）。
删了 `license.txt` 但留着 `used-cards.txt` 时，允许重新激活。

**重装丢天数的问题（已修）**

防重放上线后又暴露一个更严重的：**用户重装系统后，累加来的天数全丢**。

实测（改之前）：

```
买 3 张月卡累加到 454 天
删 license.txt（模拟重装）
用第 1 张卡恢复 → 只剩 31 天    ← 丢了 423 天
```

根因：`used-cards.txt` 只记"这张卡用过"，没记"累加到哪一天"。
恢复时只能按卡内原始到期日算，累加部分全没了。

**修法：记录每张卡激活后达到的到期日**

```
used-cards.txt 格式（TAB 分隔）：
  FINGERPRINT<TAB>EXPIRY<TAB>ISO_TIME
  0D53B72F890EECB3<TAB>2027-12-26<TAB>2026-10-29T14:45:28Z
```

恢复时取**本机历史最高到期日**兜底：比按卡内算的更晚就用历史值。

**两个必须注意的点**：

1. **必须重签卡**。只改 `finalExpiry` 不够 —— `saveLicense` 存的是原始卡，
   `status()` 里 `verifyKey(原始卡)` 返回的还是卡内日期，天数照样是 31。
   实测踩过：`stackNote` 显示找到 2028-01-25，但 `status()` 仍是 31 天。

2. **只认本机记录**。换台机器没有 `used-cards.txt`，仍按卡内日期算，
   不会变成"一张卡跨机器白拿"。这也是本地方案能接受的前提。

**实测记录**：

| 场景 | 结果 |
|---|---|
| 3 张月卡累加到 454 天 → 重装 → 卡1 恢复 | **454 天，一天没丢** ✓ |
| 重装后用卡1恢复（打包版） | 422 天 → **422 天** ✓ |
| 恢复后还能加新卡 | ✓ 491 → 498（+7）✓ |
| 恢复后同卡再刷 | ✓ 拒绝 `card-used` ✓ |

**本地方案的边界（必须诚实）**：
删掉 `%APPDATA%\UnifiedDownloader\` **整个目录**，`used-cards.txt` 一起没了，
同一张卡又能激活。真正杜绝只有服务端记录一条路。
这里的定位是堵住「手滑点两次」「同一张卡发给两个人」这类**无意重复**，
不是对抗有意的删档破解。要彻底解决必须上服务端 —— 见第 4.8.4 节的取舍说明。

**实测记录**：

| 场景 | 结果 |
|---|---|
| 同一张月卡第 2、3 次 | ✗ `card-used` 拒绝，天数不变 ✓ |
| 换新卡 | ✓ 正常累加（394 → 424）✓ |

### 🔴 26. Windows 保留端口段让 Chrome 起不来（v1.0.1 修）

**现象**（2026-10-28 实际报错）：

```
启动浏览器...
[致命] Chrome 调试端口未就绪 → exe=C:\Program Files\Google\Chrome\Application\chrome.exe
       | port=9333 | profileDir=C:\Users\Administrator\.douyin-dl-profile
```

抖音**一条都下不了**，但知乎、网页抓取都正常。

**排查关键**：必须把 Chrome 自己的 stderr 抓出来看，否则永远查不到。

```powershell
chrome.exe --remote-debugging-port=9333 --user-data-dir=<tmp> --headless=new --enable-logging=stderr
```

```
ERROR:net\socket\tcp_socket_win.cc:590] bind() returned an error:
      以一种访问权限不允许的方式做了一个访问套接字的尝试。(0x271D)
ERROR:content\browser\devtools\devtools_http_handler.cc:312] Cannot start http server for devtools.
```

**0x271D = WSAEACCES**。Windows 有一批「保留端口段」，Hyper-V / WSL / Docker
会批量占掉，落在段内的端口**谁都 bind 不了**，跟权限、跟 Chrome 版本都没关系。

本机实测（`netsh interface ipv4 show excludedportrange protocol=tcp`）：

| 引擎 | 默认端口 | 落在保留段？ | 结果 |
|---|---|---|---|
| 抖音 | 9333 | 9295–9394 ✗ | 必挂 |
| 抓取 | 9663 | 9571–9670 ✗ | 必挂 |
| 知乎 | 9444 | 不在任何段 | 正常 |

**这就是"为什么只有两个功能坏"的完整解释。**

**修法**：新增 `src/dev/port.mjs`，启动 Chrome 前先探测可用端口，
三个引擎共用（`port = await pickPort(port, warn)`）。

**写这个探测踩了两个坑（都在代码注释里留了）**：

1. **不能复用同一个 `net.Server` 实例**。error 后直接对它 `listen(新端口)`，
   Node 抛 `ERR_SERVER_ALREADY_LISTEN`，回调不触发 → 出现"明明 EACCES
   却返回可用"的假阴性。必须每次新建。
2. **`maxTries` 不能设小**。保留段是**整段连着**的，本机 9295–9394
   一次吃掉 100 个端口。上限设 40 时，从 9333 试 40 个全在段内 →
   判定"全失败"回退原端口，等于什么都没修。现在设 400。

**验证**：

```
端口 9333 不可用（Windows 保留段或被占用），自动改用 9395
CDP      : OK
```

**通用规则**：以后凡是"某个功能单独坏、其他正常"，先看它用的端口，
再抓子进程的 stderr。别急着怀疑站点风控 —— 这次就差点白查半天。

### 🟠 27. 视频不可见时报 "no aweme_detail"，用户看不懂（v1.0.1 修）

### 🟠 28. `--selftest` 跑完不退出（v1.0.1 修）

**现象**：`下载器.exe video --selftest` 打印完「自检结束」后**进程不返回**，
命令行卡住，只能 Ctrl+C。

**两个原因**（都属"定时器没清"这一类，见坑 0 / 坑 23）：

1. `spawn(chrome, ['--version'])` 那个 15 秒超时定时器没 unref、也没清
2. 自检结束只 `return`，没调 `flushAndExit`，残留的 Chrome / CDP 句柄
   把事件循环拖住

**修法**：定时器 `unref()` + 收到结果时 `clearTimeout`；结束时 `await flushAndExit(0)`。

**验证**：17.4 秒正常退出（之前会挂到天荒地老）。

**另外**：`改完就跑这个.sh` 里 `cp` 到 `src/` 那一步在 `set -e` 下会
**静默中止整个脚本**（UI 窗口开着 → 文件被占用 → 直接 exit 1，
自检根本不跑，只看到 exit=1 不知道原因）。现在改成逐个复制 + 失败给
可操作提示（"关掉 UI 窗口或 taskkill /IM 下载器UI.exe /F"）。

| 脚本 | 产物 |
|---|---|
| **`build.sh`** | **一次打全部四个 exe → `发布/bin/`** ★ 改完源码先跑这个 |
| `make-release.sh` | `发布/统一下载器-v1.0.0/`（含 ffmpeg，完整包）— *当前未生成，需要时重跑* |
| `make-release-lite.sh` | `发布/统一下载器-v1.0.0-lite.zip`（34 MB，无 ffmpeg）<br>`发布/ffmpeg-附件.zip`（31 MB）— *zip 已于 10-28 清理，附件保留* |
| `make-beta.sh` | `发布/统一下载器-v1.0.0-beta1.zip`（内测版）— *当前未生成，需要时重跑* |
| **`make-test.sh`** | **`发布/统一下载器-v1.0.1-一测（免激活·权限加固+小说接入）/` + .zip**（一测包，免激活） |
| **`make-test-ff.sh`** | **一测包（ffmpeg 内置，64.8 MB）**，两种模式：<br>`MODE=paid` → `发布/统一下载器-v1.0.0-一测（正式版·含ffmpeg·需激活）/`<br>`MODE=free` → `发布/统一下载器-v1.0.0-一测（免激活·含ffmpeg）/` |

**标准流程**：

```bash
bash 改完就跑这个.sh                 # ★ 改完源码就跑这一条，别忘
```

它会依次做完：读版本 → `build.sh` → 打两个一测包 → 同步 exe 到 `src/` → 8 项自检。
耗时约 80 秒，任一检查失败会非零退出并提示"别发货"。

**为什么必须是一条命令**：以前改完只跑 `build.sh`，产物更新了但**发布包还是旧的**。
于是出现「代码明明修好了，发给测试者的包里还是坏的那版」——
这类事故靠人记是记不住的，必须固化成一条命令。

**想单独跑某一步**：

```bash
VER=1.0.2 bash build.sh             # 只打 exe（产物进 发布/bin/）
MODE=paid bash make-test-ff.sh      # 只打「正式版」一测包（需激活）
MODE=free bash make-test-ff.sh      # 只打「免激活」一测包（给测试者）
bash make-release-lite.sh           # 正式发行包（lite + ffmpeg 附件）
bash make-beta.sh                   # 内测包
```

**版本号注入**：`VER=x.y.z bash build.sh` 会用 esbuild `--define:__VER__`
和生成 `src/gui/_version.gen.cs` 的方式改版本，**不动源码字面量**。
不传 `VER` 时，`make-test-ff.sh` 和 `改完就跑这个.sh` 会**自动从 `src/cli/cli.mjs` 读**，
避免"源码 1.0.1、脚本还写 1.0.0"这种错配（曾经发生过）。

**`build.sh` 会做的事**：

1. 检查 signtool / csc / node.exe 是否存在
2. 打包 `cli/cli.mjs` → obfuscate(AES-GCM) → SEA blob → 注入 → `发布/bin/下载器.exe`
3. 覆写 `dev/buildflag.mjs` 为 `true` → 从 `cli.mjs` 生成 `cli/cli-beta.mjs`（只改版本号）
   → 打包 → `发布/bin/下载器-beta.exe` → **立刻把开关写回 false**
4. 编译 `gui/Program.cs` 两次（带/不带 `INTERNAL_BUILD` 宏）→ `发布/bin/下载器UI.exe`
5. 打包 `dev/keygen.mjs` → obfuscate → `发布/bin/卡密生成器.exe`，并复制到 `内部工具/`
6. 打印四个产物的版本号和大小

**注意**：postject 那步比较慢（每个 exe 约 30~60 秒），
四个产物加起来要 2~3 分钟。**别以为卡死了**。

**v1.0.1 加固**：`trap 'restore_flag' EXIT` 保证构建无论成败都把
`BUILD_INTERNAL` 写回 `false` —— 否则下次打"正式版"会直接产出免授权包。

### 9.1 三个打包脚本

```bash

### 9.2 为什么拆 lite + 附件

`ffmpeg.exe` 87 MB，只在「站点视频」合并音视频时需要。
90% 的买家只用抖音 / 音乐 / 知乎 / 抓取，不需要它。

| 包 | 大小 | 内容 |
|---|---|---|
| 主包 | 36 MB | 引擎 + 界面 + 3 份用户文档 |
| ffmpeg 附件 | 32 MB | 只给需要下 B站 的人 |

主包从 174 MB 降到 36 MB，网盘下载速度问题直接解决。

### 9.3 构建流程

```
esbuild（minify）→ obfuscate → SEA blob → 复制 node.exe
→ 除签名（signtool remove）→ postject 注入 → 编译 UI → 组装目录 → zip
```

### 9.4 内测版怎么构建

`make-beta.sh` 内部：

1. `tools/make-internal-entry.mjs` 生成 `cli/cli-beta.mjs`（`BUILD_INTERNAL = true`）
2. esbuild 打包 `cli-beta.mjs`
3. 编译界面时加 `/define:INTERNAL_BUILD`（标题带「内测版」）
4. 产物改名为 `下载器-beta.exe`

### 9.5 批处理/Shell 三个坑

**① bash 里 `signtool remove /s` 要写 `//s`**

**② 中文注释会让 cmd 把后半行当命令**

`rem ── 中文 ──` 在默认代码页下解析异常。规则：
`@echo off` 前不放非 ASCII；注释尽量纯 ASCII；
文件必须 CRLF；**不要加 UTF-8 BOM**（BOM 会让第一行 `@echo` 失效）。

**③ 别用 `if exist` 判断中文路径**（见坑 15）

UI 自带自检入口：自己填字段、点按钮、采样进度、写结果、退出。

`--quiet` 拦截所有 MessageBox（一个模态框能让自动化永久卡住）。

**为什么不用外部 GUI 自动化**：多行 TextBox 在 UIA 里是 `Document`
且无 `ValuePattern`；跨进程 `WM_SETTEXT` 一写进程就崩；
标签页控件惰性建句柄。让程序自己走一遍最稳。

### v1.0.0 一测版（含 ffmpeg，2026-10-27 晚）


**两个包，各测各的**（同一份源码，只换引擎和 UI）：

| 包 | 引擎 | 用途 |
|---|---|---|
| `统一下载器-v1.0.0-一测（正式版·含ffmpeg·需激活）.zip` | `下载器.exe`（BUILD_INTERNAL=false） | 验证卡密链路：激活 → 到期 → 续费 |
| `统一下载器-v1.0.0-一测（免激活·含ffmpeg）.zip` | `下载器-beta.exe`（BUILD_INTERNAL=true） | 给测试者直接跑，**绝不能外传** |

都是 64.8 MB，ffmpeg 直接装进主包（解压即全功能）。

**为什么必须分两个**：同一个包没法既"免激活"又"验证卡密"。
免激活包的闸门在编译期就被折叠掉了，拿它测激活流程等于什么都没测；
正式版未激活时五个功能全拦（exit=2），直接给测试者会以为软件坏了。

**发售包仍走 lite（36 MB）+ ffmpeg 附件（32 MB）** —— ffmpeg 87 MB
会把主包撑到 174 MB，网盘下载体验崩。一测只发几个人，没这个压力。

#### 这一轮修的两个真 bug

**① 内测版没有镜像表 → 站点视频必挂**

内测版没有激活码 → 没有 blob → `unlockResource` 拿不到 CDN 镜像表。
于是 B站 第三方 CDN 连不上时**必然失败**，而内测版对外说的是"五个功能全部解锁"。

实测：BV1GJ411x7h7 在原 CDN 不通的网络下，内测版直接 `fetch failed`，
正式版（已激活）却能走镜像成功。

修法：`gate.mjs` 的 `INTERNAL_STATE` 内置一份镜像表，`cli.mjs` 在内测构建下
调 `internalResource()` 注入。发布版里 `BUILD_INTERNAL` 是字面量 false，
整个分支被 esbuild 折叠 —— "删掉 blob 就能白拿镜像"这条退化路径依然不存在。

**② 音频流失败会把已下好的视频一起丢掉**

实测：视频流走镜像成功 8.86 MB，紧接着音频流四个镜像**同时**不通，
重试两次后整个任务判失败 —— 已经到手的 8.86 MB 被一起扔掉，用户什么都没有。
而同样命令重跑一次就全通了（B站 CDN 本身就是波动的）。

修法：音频失败不再向上抛，改为**单独交付视频**，文件名标 `_无音轨`，
并提示"重跑一次通常就好"。

```
失败时： 【官方 MV】…_360p_无音轨.mp4   8.86 MB   ← 至少能看画面
成功时： 【官方 MV】…_360p.mp4          14.08 MB  ← 合并完整
```

解压免激活版 → 干净 APPDATA 跑 music  → exit=0（可用）✓

### 归类时踩的坑

批量替换容易写错方向：

```bash
# 第一版（错的）：cli/ 下的文件被改成了 ./engines/
s.replace("from './engines/", ...)   # ✗ cli.mjs 在 cli/ 里，./ 指的是 cli/

# 修正后
s.replace("from './engines/", "from '../engines/")    # ✓
```

**症状**：`ERR_MODULE_NOT_FOUND: Cannot find module '...\src\cli\engines\douyin-dl.mjs'`
—— 一看路径里多了 `cli/` 就知道是这个问题。

### 构建入口也变了

```bash
# 旧
npx esbuild cli.mjs --bundle ...
node obfuscate.mjs build/all-bundle.raw.cjs build/all-bundle.cjs

# 新
npx esbuild cli/cli.mjs --bundle ...
node dev/obfuscate.mjs build/all-bundle.raw.cjs build/all-bundle.cjs
```

`sea-all.json` 里的 `"main": "build/all-bundle.cjs"` **不用改**（相对路径基于 cwd）。
